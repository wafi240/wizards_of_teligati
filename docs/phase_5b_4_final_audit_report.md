## 2. Comprehensive Inventory of Discovered & Resolved Issues

| Component | Issue Identified | Security / Reliability Impact | Resolution & Verification |
|---|---|---|---|
| **Backend `ProfileService`** | Missing role-specific attribute validation in profile updates (`PUT /api/v1/profiles/me`) | A malicious student user could submit JSON payloads updating faculty-specific attributes (`designation`, `researchFocus`, `labName`, `publicationsCount`) or alumni hiring status (`isActivelyHiring`). | Enforced role-bound attribute validation in `ProfileService.updateProfile()`. Any update attempt containing unauthorized role attributes triggers an immediate `BadRequestException` (HTTP 400). Covered by 6 automated tests in `ProfileDirectoryTest`. |
| **Backend `DirectoryController`** | Unbounded/negative pagination query parameters | Negative page indices or zero/negative page sizes could trigger uncaught Spring Data JPA `IllegalArgumentException` (HTTP 500) or denial-of-service via massive page requests. | Implemented strict parameter clamping: `safePage = Math.max(0, page)` and `safeSize = (size <= 0) ? 20 : Math.min(size, 100)`. Covered by unit and integration tests. |
| **Backend Database Schema** | Column data type mismatch for `cgpa` in `V3__profile_directory_expansion.sql` | Hibernate 6 mapped Java `Double` to `double precision` / `float8`, whereas SQL migration originally used `NUMERIC(3, 2)`, causing Hibernate DDL validation failure on fresh PostgreSQL instances. | Aligned migration script `V3__profile_directory_expansion.sql` to `DOUBLE PRECISION`. Verified schema initialization in `MigrationV3Test`. |
| **Android `AppRepository`** | Stale fallback query in `getAlumniProfile()` leaking User #1 | When querying an alumni profile for a newly authenticated user whose ID had not yet populated the local cache, `if (profile == null) profile = db.profileDao().getAlumniProfileById(1);` returned the profile of User #1. | Eliminated the hardcoded fallback to `id = 1`. Now falls back strictly to the authenticated user's active session attributes. |
| **Android `ProfileRepository`** | Stale fallback in `loadCachedProfileFromRoom()` | Similar to `AppRepository`, querying an alumni profile fell back to `getAlumniProfileById(1L)`. | Removed hardcoded fallback to record 1. Profile caching now strictly adheres to the active session user ID. |
| **Android `ProfileRepository`** | Room Primary Key duplication during profile cache sync | `syncProfileToRoom()` constructed new entity objects (`AlumniProfileEntity`, `TeacherProfileEntity`) without checking existing row IDs, resulting in duplicate entries upon subsequent syncs. | Added pre-sync check: queries existing entity ID by `userId` and sets `entity.setId(existing.getId())` so Room updates the existing row in place. |
| **Android `ApiClient`** | Bearer authorization token exposure in Logcat logs | HTTP request logs generated by OkHttp `HttpLoggingInterceptor` included cleartext `Authorization: Bearer <jwt_token>` headers. | Added `loggingInterceptor.redactHeader("Authorization");` ensuring access tokens are redacted in all debug log streams. |
| **Android `StudentAlumniDirectoryFragment`** | Asynchronous race condition between Room cache & remote API | When browsing directories, the local Room cache query ran concurrently with the network API call. If the Room query resolved *after* the remote call, outdated local data overwrote fresh remote results. | Added sequence version tracking (`currentLoadVersion`) and `isRemoteLoaded` flags. Out-of-order local responses are silently discarded once remote results have been displayed. |
| **Android UI & Search Filters** | NullPointerExceptions during directory filtering on sparse profiles | Calling `.toLowerCase()` directly on nullable profile fields (`company`, `city`, `designation`, `department`) caused app crashes when searching. | Added robust null checks across `StudentAlumniDirectoryFragment` and `TeacherStudentResearchersFragment`. |
| **Android `ProfileFragment`** | Display glitch: `"null @ null • null"` | When optional profile attributes were missing, formatting string rendered literal `"null"` tokens to the user. | Added conditional formatting checking each string component before assembly. |

## 3. Backend Profiles & Directory Audit Details

### 3.1 Authentication & Profile Ownership
- **Endpoint:** `GET /api/v1/profiles/me` and `PUT /api/v1/profiles/me`
- **Security Control:** Authenticated user identity is resolved solely via the server-validated JWT `SecurityContextHolder.getContext().getAuthentication().getPrincipal()`. The client cannot supply a `userId` in the payload to modify another user's profile.
- **Role Immutability:** User roles (`STUDENT`, `ALUMNI`, `FACULTY`, `ADMIN`) are stored in the immutable `users` table. The `ProfileUpdateRequest` DTO does not expose any role parameter, preventing privilege escalation.
- **Verification Immutability:** `isVerified` is server-managed and cannot be altered through profile update requests.

### 3.2 Role-Specific Attribute Restrictions
The backend enforces business rules ensuring profile modifications match the caller's role:
- **`STUDENT`**:
  - Allowed: `bio`, `phone`, `skills`, `linkedinUrl`, `githubUrl`, `portfolioUrl`, `specialization`, `cgpa`, `clubs`, `isAvailableForMentorship`, `isActivelyHiring`.
  - Forbidden: Faculty-specific fields (`designation`, `researchFocus`, `labName`, `publicationsCount`, `contactEmail`).
  - Attempting to submit faculty attributes returns `400 Bad Request` with message: `"Students cannot set faculty-specific profile attributes"`.
- **`FACULTY`**:
  - Allowed: `bio`, `phone`, `skills`, `linkedinUrl`, `githubUrl`, `portfolioUrl`, `designation`, `researchFocus`, `labName`, `publicationsCount`, `contactEmail`.
  - Forbidden: Student-specific fields (`cgpa`, `clubs`, `specialization`).
  - Attempting to submit student attributes returns `400 Bad Request` with message: `"Faculty members cannot set student-specific profile attributes"`.
- **`ALUMNI`**:
  - Allowed: `bio`, `phone`, `skills`, `linkedinUrl`, `githubUrl`, `portfolioUrl`, `company`, `designation`, `experienceYears`, `city`, `country`, `isAvailableForMentorship`, `isActivelyHiring`.
  - Forbidden: Student-specific fields (`cgpa`, `clubs`, `specialization`) and faculty-specific fields (`researchFocus`, `labName`, `publicationsCount`, `contactEmail`).
  - Attempting to submit forbidden attributes returns `400 Bad Request`.

### 3.3 Privacy & Public Directory Protection
- **Endpoints:**
  - `GET /api/v1/directory/students`
  - `GET /api/v1/directory/alumni`
  - `GET /api/v1/directory/faculty`
- **Privacy Enforcement:**
  - Directory responses return `DirectoryProfileResponse` projections.
  - Sensitive internal authentication details (passwords, refresh token hashes, soft-delete states) are omitted.
  - Non-verified accounts can be filtered via query parameter `?verifiedOnly=true`.
  - Directory search queries (`department`, `search`, `skills`, `company`, `availableForMentorship`, `activelyHiring`) execute case-insensitive `ILIKE` database queries.
- **Pagination Boundary Clamping:**
  - Negative page parameters (`?page=-1`) are clamped to `0`.
  - Zero or negative page sizes (`?size=0` or `?size=-5`) default to `20`.
  - Excessive page sizes (`?size=99999`) are clamped to maximum `100`.

## 4. Android Integration Audit Details

### 4.1 Token Handling & Session Isolation
- **Token Storage:** Tokens are managed via `SessionManager`, using Android Keystore-backed `EncryptedSharedPreferences`. In production Android runtime, no plaintext fallback is permitted.
- **No Token/Credential Persistence in Room:** Local Room entities (`UserEntity`, `ProfileEntity`, `AlumniProfileEntity`, `TeacherProfileEntity`) do not contain password hashes, access tokens, or refresh tokens.
- **Header Redaction:** `ApiClient` configures `HttpLoggingInterceptor.redactHeader("Authorization")` to eliminate token leakage in Logcat.
- **Account Switching & Cache Isolation:**
  - When switching users, `SessionManager.clearSession()` wipes in-memory and encrypted credentials.
  - Room profile queries are keyed strictly to the active user's `userId`.
  - Stale fallbacks (`getAlumniProfileById(1)`) have been eliminated.

### 4.2 Offline Cache & Synchronization Strategy
- **Read Path (Directory):**
  1. Displays cached data from Room immediately to keep UI responsive.
  2. Issues asynchronous network request to Spring Boot backend via Retrofit.
  3. On successful network response, updates the UI and persists new records into Room.
  4. Sequence-version check prevents delayed local queries from overwriting fresh remote data.
- **Write Path (Profile Update):**
  1. Validates input format on client.
  2. Dispatches `PUT /api/v1/profiles/me` network request.
  3. Upon 200 OK response, maps the updated `ProfileResponse` to local Room entities and commits via background thread.
  4. Preserves existing Room primary keys to avoid duplicate entity creation.

## 6. Architecture & Scope Boundary Compliance

1. **No Scope Creep:**
   - No Phase 5B.5 domain entities (Opportunities, Gigs, Research Proposals, Job Applications, Transactions) have been migrated to the backend or removed from Android Room.
   - All gig, proposal, and transaction operations remain safely handled by local Room entities and DAOs until their dedicated phase.
2. **Preserved Android UX & Architecture:**
   - Existing UI themes, cyber/KUET styling, bottom navigation, toolbar action menus, and drawer navigation remain intact.
   - Navigation flows between dashboards (`StudentDashboardFragment`, `AlumniDashboardFragment`, `TeacherDashboardFragment`) operate smoothly.
3. **Security Standards Maintained:**
   - Passwords hashed with BCrypt.
   - JWT access tokens (15-min TTL) and refresh tokens (7-day TTL with rotation and revocation) remain strictly enforced.
   - Production profiles disallow hardcoded demo credentials.

## 7. Known Limitations & Recommended Phase 5B.5 Roadmap

### Known Limitations (By Design for Phase 5B.4)
1. **Avatar & Document File Uploads:**
   - Current profile photo (`avatarUrl`) and resume links are stored as URLs/strings. Actual multipart binary upload (S3 / MinIO / local disk storage) is scheduled for the media storage milestone.
2. **Gigs, Applications & Reference Requests:**
   - Remain local in Room (`JobOpportunityEntity`, `ResearchOpportunityEntity`, `ApplicationEntity`, `ReferenceRequestEntity`) as planned.
3. **Public Mentorship Toggle:**
   - `isAvailableForMentorship` is toggled via `ProfileUpdateRequest`. A quick 1-click toggle directly from dashboard cards will be connected once the Opportunities API is implemented.
