# Wizards of Teligati — Phase 5B.9: Messaging & Communication Report

## 1. Executive Summary

Phase 5B.9 implements and integrates a secure, role-aware messaging and communication system across the Spring Boot backend and the Android application for the KUET community (Students, Alumni, and Teachers).

### Key Accomplishments
1. **Canonical Conversation Model**:
   - Single canonical conversation thread per participant pair enforced via database constraint `UNIQUE (participant1_id, participant2_id)` and order constraint `chk_participant_order CHECK (participant1_id < participant2_id)`.
   - Prevents duplicate conversation threads and race conditions.
2. **Secure One-to-One Messaging**:
   - Enables bidirectional messaging across all roles (Student ↔ Alumni, Student ↔ Teacher, Alumni ↔ Alumni, Alumni ↔ Teacher, Student ↔ Student).
   - Rejects self-messaging with descriptive validation errors (`HTTP 400 Bad Request`).
   - Enforces participant authorization: users cannot read or send messages in conversations they do not belong to (`HTTP 403 Forbidden`).
3. **Receipts & Unread Tracking**:
   - Message delivery and read receipts (`isRead`, `readAt`, `sentAt`).
   - Dynamic unread count calculation per user.
   - Batch mark-as-read endpoints at conversation level and single-message level.
4. **Notification Integration**:
   - Integrated with existing `NotificationService` to automatically deliver `NEW_MESSAGE` notifications to message recipients without duplicating notification logic.
5. **Offline-First Android Integration**:
   - Local Room storage updated with `ConversationEntity` and upgraded `MessageEntity`.
   - `MessagingRepository` performs local-first cache updates, remote synchronization via Retrofit, and background database writes.
   - Enhanced `MessagesFragment` with active conversation thread selection, real-time message bubble rendering (`MessageAdapter`), read receipt indicators, and direct response capabilities.
   - Connected `NotificationsFragment` so tapping a `NEW_MESSAGE` notification immediately deep-links into the relevant chat thread.

## 2. Database Schema Changes (Flyway Migration V8)

### Migration Script: `V8__messaging_and_conversations.sql`
Location: `backend/src/main/resources/db/migration/V8__messaging_and_conversations.sql`

```sql
-- Conversations Table
CREATE TABLE IF NOT EXISTS conversations (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    participant1_id BIGINT NOT NULL,
    participant2_id BIGINT NOT NULL,
    last_message_text TEXT,
    last_message_at TIMESTAMP WITHOUT TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    created_at TIMESTAMP WITHOUT TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    updated_at TIMESTAMP WITHOUT TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT fk_conversations_p1 FOREIGN KEY (participant1_id) REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT fk_conversations_p2 FOREIGN KEY (participant2_id) REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT uk_conversations_participants UNIQUE (participant1_id, participant2_id),
    CONSTRAINT chk_participant_order CHECK (participant1_id < participant2_id)
);

CREATE INDEX IF NOT EXISTS idx_conversations_p1 ON conversations (participant1_id);
CREATE INDEX IF NOT EXISTS idx_conversations_p2 ON conversations (participant2_id);
CREATE INDEX IF NOT EXISTS idx_conversations_last_msg ON conversations (last_message_at);

-- Messages Table
CREATE TABLE IF NOT EXISTS messages (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    conversation_id BIGINT NOT NULL,
    sender_id BIGINT NOT NULL,
    recipient_id BIGINT NOT NULL,
    content TEXT NOT NULL,
    is_read BOOLEAN DEFAULT FALSE NOT NULL,
    read_at TIMESTAMP WITHOUT TIME ZONE,
    created_at TIMESTAMP WITHOUT TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL,
    CONSTRAINT fk_messages_conversation FOREIGN KEY (conversation_id) REFERENCES conversations (id) ON DELETE CASCADE,
    CONSTRAINT fk_messages_sender FOREIGN KEY (sender_id) REFERENCES users (id) ON DELETE CASCADE,
    CONSTRAINT fk_messages_recipient FOREIGN KEY (recipient_id) REFERENCES users (id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_messages_conversation ON messages (conversation_id);
CREATE INDEX IF NOT EXISTS idx_messages_sender ON messages (sender_id);
CREATE INDEX IF NOT EXISTS idx_messages_recipient ON messages (recipient_id);
CREATE INDEX IF NOT EXISTS idx_messages_created ON messages (created_at);
```

## 3. Backend Architecture & API Endpoints

### 3.1 Entities & Repositories
- **`com.teligati.backend.entity.Conversation`**: JPA entity maintaining canonical participant ordering, last message previews, and audit timestamps.
- **`com.teligati.backend.entity.Message`**: JPA entity holding conversation linkage, sender, recipient, text content, read flags, and timestamps.
- **`ConversationRepository`**: Queries conversations for a user by participant IDs (`participant1.id = :userId OR participant2.id = :userId`), looks up existing pair conversations, and calculates unread counts.
- **`MessageRepository`**: Fetches conversation messages in ascending chronological order (`findByConversationIdOrderBySentAtAsc`), counts unread messages for a recipient, and marks messages as read.

### 3.2 Services & Concurrency Safety
- **`MessagingService`**:
  - `getOrCreateConversation(currentUser, recipientId)`: Canonicalizes IDs (`min(user1, user2)`, `max(user1, user2)`), verifies recipient existence, prevents self-messaging, and synchronizes on an interned participant pair key (`conv_pair_p1_p2`) inside a dedicated `TransactionTemplate` to guarantee thread safety against concurrent creation.
  - `getUserConversations(currentUser)`: Returns all conversations with partner details, last message summary, and unread count.
  - `getMessages(currentUser, conversationId)`: Enforces conversation membership before returning message history.
  - `sendMessage(currentUser, conversationId, request)`: Validates text length, creates message with server-controlled timestamps, updates conversation last message preview, and triggers `NotificationService.createNotification(recipient, "New Message from ...", NEW_MESSAGE, referenceId)`.
  - `markMessageRead(currentUser, messageId)` & `markConversationRead(currentUser, conversationId)`: Updates read status and timestamps strictly for messages where the authenticated user is the recipient.

### 3.3 REST Endpoints

| Method | Endpoint | Description | Access |
|---|---|---|---|
| `GET` | `/api/v1/conversations` | Lists all conversations for current user with unread counts | Authenticated |
| `POST` | `/api/v1/conversations` | Initiates or returns existing canonical conversation with target user | Authenticated |
| `GET` | `/api/v1/conversations/{id}/messages` | Retrieves message history for conversation (in chronological order) | Participant only |
| `POST` | `/api/v1/conversations/{id}/messages` | Sends a message in the specified conversation | Participant only |
| `PATCH` | `/api/v1/conversations/{id}/read` | Marks all unread messages received in conversation as read | Participant only |
| `PATCH` | `/api/v1/messages/{id}/read` | Marks a specific message as read | Recipient only |

### 4.1 Network Models & API Service

### 4.3 Repositories & UI Integration

  - Renders incoming vs. outgoing speech bubbles with distinct alignments, background tints, timestamps, and read receipt checkmarks.
- **`NotificationsFragment`**:

In the initial test run, an exit code 1 occurred due to two specific causes:

2. **Gradle Concurrency Lock**: Two Gradle test processes attempted to write to `backend/build/test-results/test` simultaneously. Running a clean test resolved the file contention.

### 5.5 Messaging Security Verification

In `MessagingDomainTest`:
1. **Access Control**: Non-participants attempting to fetch messages via `GET /api/v1/conversations/{id}/messages` receive `HTTP 403 Forbidden`.
2. **Send Authorization**: Non-participants attempting to post messages via `POST /api/v1/conversations/{id}/messages` receive `HTTP 403 Forbidden`.
3. **Impersonation Prevention**: Sender identity is strictly derived from the authenticated JWT `principalName`. The request payload has no `senderId` field.
4. **Read Status Integrity**:
   - Senders cannot mark their own messages as read (`HTTP 403 Forbidden`).
   - Only the message recipient can update read receipts (`HTTP 200 OK`, `isRead = true`, `readAt` set).
5. **Self-Messaging**: Attempting to create a conversation where sender ID equals recipient ID returns `HTTP 400 Bad Request`.
6. **Server-Controlled Timestamps**: All `createdAt`, `updatedAt`, `sent_at`, and `read_at` timestamps are generated server-side.
7. **Invalid IDs**: Non-existent conversation IDs return `HTTP 404 Not Found`.

### 5.6 Message Delivery Strategy

- **Identified Delivery Strategy**: **REST Polling / Manual On-Demand Refresh**.
- **Important**: The current implementation does **NOT** use WebSockets. Real-time persistent sockets are not active; communication operates via HTTP REST endpoints.
- **Offline Receiver Behavior**: Messages are safely committed to PostgreSQL/H2, flagged `is_read = false`, and recorded in the recipient's unread counter. When the receiver opens the app or returns to the conversation, the messages load and are marked read.
- **Offline Sender Behavior**: `MessagingRepository` stores outgoing messages in local Room storage immediately, allowing UI continuity. When connectivity is restored, the next sync synchronizes with the backend.
- **Retry Behavior**: Conversation creation is idempotent. Resending duplicate messages with identical payloads results in separate distinct messages with unique sequential IDs.
